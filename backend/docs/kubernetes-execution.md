# Kubernetes execution backend

The `kubernetes` worker backend implements the existing asynchronous `execution.Controller` contract. It creates one deterministic Kubernetes Job named `coyote-exec-<execution-job-id>` per durable execution job and keeps the Coyote database claim and lease authoritative.

The controller renews the execution and step lease while the Job is pending or running. A restarted controller can reclaim the execution, derive the same Job name, and resume observing it. Kubernetes Job metadata has Coyote execution/build/node/attempt labels, but never claim tokens or credentials. Jobs use `backoffLimit: 0`; Coyote owns retry decisions.

When workspace-revision storage is configured, each execution Pod uses one shared `emptyDir` mounted at `/workspace` with this lifecycle: `workspace-prepare` init helper, `build`, then `workspace-publish`. The helpers reuse the worker image and the existing internal workspace prepare/publish transports. The prepare helper materializes source-backed workspaces and restores predecessor revisions before the build starts. The publish helper waits for the Kubernetes API to report that its own Pod UID matches and that the `build` container terminated with exit code `0`; only then does it obtain its publish capability and publish the revision. A nonzero build exit skips publication. Therefore Job success means preparation, build, and trusted publication all succeeded before the controller finalizes the Coyote execution.

The Pod has `automountServiceAccountToken: false`. The build container receives only the workspace mount and its repository command environment: it has no projected helper token, helper capability, Kubernetes API token, database credentials, SCM credentials, workspace-store credentials, or controller kubeconfig. The prepare helper mounts only its prepare-audience token. The publish helper mounts only its publish-audience token plus a separate Kubernetes API-audience token, CA bundle, and namespace identity to `get` its own Pod status. The helper ServiceAccount requires only namespace-scoped `get` on Pods.

Source, predecessor, and isolated writable descendant (fan-out) workspace plans are supported by the helper lifecycle. Portable fan-in remains rejected, as do cache restore/save and artifact collection. Cancellation remains DB-first: the controller deletes canceled Jobs and the existing capability/claim checks prevent stale helper publication from becoming authoritative. If a helper publication has already reached the authoritative revision state when a controller restarts, the deterministic Job is simply observed to completion and the controller finalizes without republishing. Prepare or publish helper failures are reported as workspace failures; build exits remain execution failures, and Kubernetes deadline expiry remains a timeout.

Terminal build-container logs are collected through the Pod logs API and appended to the existing Coyote log sink before lifecycle completion. Within a controller process, terminal log content is persisted at most once per execution job, so a completion retry cannot duplicate it; a log read/write failure defers completion and is retried. There is intentionally no restart-safe log cursor yet, so exact-once log persistence across controller restarts remains deferred. Exit `0` finalizes through the existing token-guarded build/step/job completion path; non-zero exits use the existing execution failure classification, and a true Kubernetes `JobFailed` condition with reason `DeadlineExceeded` uses timeout classification. Cancellation remains DB-first: the controller sweeps Coyote-managed Jobs at a bounded periodic interval and idempotently deletes ones whose durable execution is canceled, including after controller restart and while other work is active.

The controller service account needs namespace-scoped `get`, `list`, `watch`, `create`, and `delete` on Jobs; `get`, `list`, and `watch` on Pods; and `get` on `pods/log`. Build Pods must not use the controller service account and must not receive Coyote database, Kubernetes-controller, workspace-store, or kubeconfig credentials. This is an initial control-plane slice, not a production-ready workspace transport.
