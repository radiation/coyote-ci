# Kubernetes execution backend

The `kubernetes` worker backend implements the existing asynchronous `execution.Controller` contract. It creates one deterministic Kubernetes Job named `coyote-exec-<execution-job-id>` per durable execution job and keeps the Coyote database claim and lease authoritative.

The controller renews the execution and step lease while the Job is pending or running. A restarted controller can reclaim the execution, derive the same Job name, and resume observing it. Kubernetes Job metadata has Coyote execution/build/node/attempt labels, but never claim tokens or credentials. Jobs use `backoffLimit: 0`; Coyote owns retry decisions.

This initial backend supports only one checkout-free, single-step execution with a source workspace input, no cache, no artifact declarations, and no configured workspace-revision storage. The Pod mounts an `emptyDir` at `/workspace`, and the build container has `automountServiceAccountToken: false`. Repository checkout, workspace restore/publication, multi-step pipelines, fan-out/fan-in, caches, and artifacts are rejected before Job creation.

Terminal build-container logs are collected through the Pod logs API and appended to the existing Coyote log sink before lifecycle completion. Within a controller process, terminal log content is persisted at most once per execution job, so a completion retry cannot duplicate it; a log read/write failure defers completion and is retried. There is intentionally no restart-safe log cursor yet, so exact-once log persistence across controller restarts remains deferred. Exit `0` finalizes through the existing token-guarded build/step/job completion path; non-zero exits use the existing execution failure classification, and a true Kubernetes `JobFailed` condition with reason `DeadlineExceeded` uses timeout classification. Cancellation remains DB-first: the controller sweeps Coyote-managed Jobs at a bounded periodic interval and idempotently deletes ones whose durable execution is canceled, including after controller restart and while other work is active.

The controller service account needs namespace-scoped `get`, `list`, `watch`, `create`, and `delete` on Jobs; `get`, `list`, and `watch` on Pods; and `get` on `pods/log`. Build Pods must not use the controller service account and must not receive Coyote database, Kubernetes-controller, workspace-store, or kubeconfig credentials. This is an initial control-plane slice, not a production-ready workspace transport.
